# 性能预算（阈值与测量方法）

> 对应铁律 27。本文件补上 spec 长期缺失的「判据」——此前只有实测素材（60.1 s / 685.4 MB / 11.4 MB/s），没有一条把上限写成可判定的门槛。

## 一、阈值

| 场景 | 上限 | 判据 |
| --- | --- | --- |
| 交互反馈（点击、切换图表、勾选） | **100 ms** | 从事件到首帧可见更新的耗时 |
| 本地部署从宿主拉取（整包） | **10 s** | 从点击到浏览器出现下载完成 |
| 相对宿主原生 | **不得更慢** | 同等数据量下，插件耗时 ≤ 宿主原生耗时 |
| 插件首屏 | **即时**，不出现空白等待 | 打开插件到可交互 |
| 教程浮层 | **即时**，不得"操作几次后才弹出" | 首次进入插件即出现 |

## 二、门槛与实测的关系

既有实测记录（如整包 60.1 s、吞吐 ~300 KB/s）属于**事故基线**，不是目标值，二者不得混写：

- 事故基线 → 记在本文件的「历史实测」小节，用于回归比对
- 目标阈值 → 只有上表，任何实现必须满足上表

当实测与阈值冲突时，**以阈值为准，实测记为待修缺陷**，不得反向把阈值改成实测值。

## 三、测量方法

1. 交互延迟：在 Dev 实例用 Playwright 无头浏览器打点，取 `performance.now()` 差值，重复 5 次取中位数。
2. 拉取耗时：从点击到 `download` 事件完成，计时一次；不足 10 s 视为通过。
3. 相对原生：同包同环境各跑一次，比较两次总耗时。
4. 首屏与教程浮层：从插件面板打开到目标节点可见的耗时。

## 四、历史实测（仅作回归参照）

| 场景 | 实测 | 归因 |
| --- | --- | --- |
| 大包转换 | 685.4 MB / 60.1 s / 11.4 MB/s | 分块与 OPFS 直写路径 |
| 局域网接收 | 吞吐 ~300 KB/s | 每块全量重绘导致串行瓶颈；已由 rAF 合帧改善 |
| 进度回调 | 单次 14 个 80–107 ms 长任务 | 未合帧 |
| 宿主拉取 | 比原生慢约 20 倍（约 1 MB/s） | 逐块写入固定开销 |

## 五、回归要求

改动涉及 `src/core/**`、`src/ui/host-bridge.js`、分块/写入路径时，必须在 Dev 实例复测上表前三项，并在 PR 说明里贴出实测数字；未测不得声称性能达标。
